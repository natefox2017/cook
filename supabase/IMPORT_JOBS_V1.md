# Import Jobs V1 — implementation and deployment boundary

This directory adds the **first server job/queue slice** for [Issue #31](https://github.com/natefox2017/cook/issues/31). V1 uses the durable PGMQ queue `recipe_import_v1`, created by this migration. The pre-existing `recipe_import` queue remains owned by legacy producers and consumers.

## Data flow

- The signed-in user calls `POST /functions/v1/recipe-imports` with a validated `client_request_id` and a text, HTTPS URL, or confirmed owner artifact reference. Image/PDF sources are uploaded through `recipe-import-artifacts`; cloud processing retains their evidence and finishes as `needs_review` because this non-AI slice does not run OCR/ASR.
- `recipe-imports` authenticates the bearer token against Supabase Auth. Owner is derived from the verified token again in `submit_own_recipe_import` via `auth.uid()`, never accepted in JSON. Anonymous-auth users are not eligible.
- The SQL RPC locks per owner, checks a 30-new-jobs/hour limit and `(owner_id,client_request_id)` uniqueness, creates a private job row and sends PGMQ message **in the same database transaction**. Only then does the response advertise `queued`. If insertion, queue send or commit fails, no false queued job is acknowledged.
- `GET /functions/v1/recipe-imports/{job_id}` fetches only the signed-in owner's job (RLS + explicit owner predicate). `POST /.../{job_id}/retry` reuses the existing job when its failed error is recoverable and attempts remain, with transactional queue re-admission.
- `recipe-import-worker` is service-only and triggered by an authenticated secret. It uses dedicated `recipe_import_v1_queue_read` and `recipe_import_v1_queue_archive` RPCs plus the new server-only atomic claim. These wrappers name only `recipe_import_v1`; the legacy RPCs still name only `recipe_import`. The queues and consumers therefore cannot claim one another's messages. Unacknowledged messages become visible again; stale claims can be retried up to three attempts. **Queue archive occurs only after the job result is persisted.**
- For **pasted text**, the small evidence-first extractor reads explicit Ingredients/Steps headings in English/Chinese/Japanese, preserves vague amounts as null normalization and marks incomplete results `needs_review`.
- For **public HTTPS webpages**, the worker resolves each hostname to IPv4, rejects any non-public answer, and passes only the validated address list to a one-request HTTPS lookup while retaining the original hostname for TLS SNI and certificate validation. It does not auto-follow redirects: every redirect is revalidated and resolved again. Requests are limited to port 443, three redirects, 10 seconds total, 1.5 MB, identity encoding, and HTML/XHTML MIME types.
- The webpage parser reads only Schema.org Recipe JSON-LD. It keeps original URL, final URL, page title, author, raw JSON-LD evidence, and verbatim ingredient/instruction strings. Missing fields and pages with multiple Recipe objects become explainable `needs_review` results; it never fills in quantities. Video pages, login/interstitial pages, and dynamically rendered content are unsupported. A shared PDF is stored as a private source artifact; the worker does not extract its text.
- Private image/PDF artifacts use the `recipe-import-artifacts` bucket and owner-scoped metadata. A two-hour upload intent is confirmed against the stored object size, MIME and file signature; complete uploads expire after seven days. Reads use a one-minute signed URL. The owner-scoped API delete operation and account-delete flow remove objects through the Storage API; the current app has no individual artifact-delete control. The cleanup function expires stale uploads and old source files when invoked by a trusted project scheduler; deployment must configure that daily invocation and its server-only secret.
- Results live in the private job payload. The authenticated iOS share workflow uploads attachments, submits URL/text/artifact jobs, polls status and maps completed results while preserving user edits. Since image/PDF parsing is not part of this non-AI slice, attachment jobs keep source evidence and finish as `needs_review`; local Vision/PDFKit import remains available in the manual Add Recipe flow.

## 2026-10-08 source audit and lease-fencing changes

- **SQL idempotency:** original user source bytes remain in `source_value`, while the trimmed copy is used only for basic input validation and an index hint. Repeating the exact same `client_request_id` and original text with leading/trailing whitespace now returns the existing job rather than a false 409. Changing the original text with the same request ID still conflicts.
- **Worker lease fencing:** terminal `failed`/`completed` updates now compare both `queue_message_id` and the attempt number returned by `claim_recipe_import_job`. When a visibility timeout permits a fresh claim, a stale worker cannot overwrite the new attempt's final status or result. The losing worker must leave the message unacknowledged.
- **SQL source audit:** one definition each of submit/retry/claim is present; the accidental earlier concatenation has not recurred. This is a source-level check, **not PostgreSQL syntax/runtime proof**.
- **Queue compatibility decision:** V1 creates and uses a distinct `recipe_import_v1` queue, with its own service-only read/archive wrappers. Legacy `recipe_import_enqueue`/`recipe_import_enqueue_many` and their consumers remain on `recipe_import`; their `pending/running/imported` lifecycle is not adapted to the V1 job table. No V1 producer emits to the legacy queue, and no V1 worker reads or archives from it. This isolates both protocols without requiring the old producer/consumer to be retired before V1 deployment.
- **Read-only production check:** the legacy queue exists and `public.recipe_import_jobs` is absent. The legacy `recipe_import_enqueue` function still writes `pending/running/imported` and references columns absent from this V1 table. The migration does not inspect, move, archive, or delete legacy messages.
- **Required database regressions:** (1) exact whitespace-bearing request replay -> same job ID; (2) same request ID with different raw text -> conflict; (3) worker A claims attempt N, times out, worker B claims attempt N+1, then A's fenced write changes **zero rows**; (4) B persists final result before ACK; (5) account A cannot query or retry account B's job. Run on a disposable database with real authenticated roles before deploying.

## Private artifact configuration

- Apply the artifact migration before deploying `recipe-import-artifacts` or enabling `image` / `file` import requests.
- Set `RECIPE_IMPORT_ARTIFACT_CLEANUP_SECRET` only in the Edge Function environment. Invoke `purge-expired-recipe-import-artifacts` from the trusted project scheduler at least daily with `Authorization: Bearer <secret>`; never put this secret in iOS configuration.
- The private bucket has no end-user Storage object policies. The authenticated artifact function verifies the caller against `owner_id` before upload, read or delete operations; signed URLs are short-lived. Account deletion also removes the bucket prefix for that owner.
- Current file support is JPEG, PNG, HEIC/HEIF, PDF and UTF-8 text up to 10 MiB. Cloud import preserves the private source evidence and returns `needs_review`; the worker does not inspect image pixels or PDF text.

## 2026-10-08 public webpage extraction follow-up

- **Parser selection:** evaluated the MIT TypeScript [`recipe-scrapers`](https://github.com/recipe-scrapers/recipe-scrapers) package (v3.2.0). Its generic Schema.org path worked on the public-page capture, but its validated Recipe object rejects a Recipe without an author and adds host-specific/OpenGraph extractors. Since this slice must preserve partial JSON-LD without inventing missing author/yield data, the worker uses Cheerio for HTML script extraction and a narrow Schema.org `Recipe` mapper instead. `ipaddr.js` is pinned for IANA special-range classification.
- **SSRF implementation:** Deno's documented DNS and TCP/TLS APIs are available in Deno 2.x; Supabase says hosted Edge Functions run a Deno 2.1-compatible runtime. The HTTPS client pins custom lookup results while retaining the original hostname for TLS verification. The generic Deno host test successfully fetched the public BBC Good Food recipe using pinned Fastly IPv4 addresses. Every redirect fixture resolves the next hostname independently; private, special-purpose, or mixed address sets fail before a request is made.
- **Local resolver boundary:** this workstation's default DNS path answers public hostnames with `198.18.0.54`, an IANA benchmarking range, so the production resolver correctly rejects it. The live integration test used a test-only DNS-over-HTTPS resolver to obtain public BBC addresses, then exercised the production pinned-HTTPS request and JSON-LD parser against the live page. The production resolver has no DoH fallback.
- **Supabase runtime boundary:** the isolated CLI native database stack applied migration history with a temporary legacy-RPC stub, but `supabase functions serve` could not start because Docker/Podman is unavailable. Therefore hosted/CLI Edge Runtime socket permission and its DNS behavior are **not verified** here. Keep the PR Draft until the target isolated Edge Runtime test proves those boundaries; if it cannot use pinned sockets, keep URL processing disabled and use a trusted SSRF egress proxy as described above. No API contract, queue schema, #72 client interface, production data, or device state changed.
- **Executed tests:** `safeURLFetch_test.ts` (7/7) and `schemaRecipe_test.ts` (4/4) passed; opt-in `safeURL_live_test.ts` fetched and parsed BBC Good Food's Easy Chocolate Cake page (1/1). This confirms the local Deno implementation and real-page JSON-LD, not Supabase Edge Runtime or production acceptance.

## 2026-10-08 frozen-request conformance follow-up

- The existing OpenAPI request schema permits optional `original_source_url` and `platform_hint`, while rejecting unknown properties and mixed URL/text/artifact inputs. The HTTP handler now enforces that shape, persists original source URL metadata, returns it in text and web results, and treats changes to either optional metadata field on an idempotency replay as a conflict. The four-argument SQL primitive is no longer directly executable by authenticated clients; the HTTP API uses the owner-checked five-argument wrapper.
- The additive migration preserves existing rows and does not touch either queue. It was created after the V1 migration and does not rewrite the published OpenAPI/JSON Schema or status contract.
- **Rollback boundary:** this migration has not been applied to production. If the five-argument endpoint needs to be rolled back after application, switch the Edge API back to the four-argument RPC and restore its `authenticated` EXECUTE grant; keep the nullable metadata column and any stored values. Do not drop or rewrite either PGMQ queue. Remove the added column only in a later, separately reviewed cleanup after confirming no stored metadata depends on it.
