# 产品基线 V1

## 1. 产品定位

Cook 是个人食谱收集与烹饪工具。

核心价值：
> 把用户在第三方平台刷到的做饭内容，以接近“收藏一次视频”的成本，自动变成可以直接照着做的结构化食谱。

产品路径参考 ReciMe、Recipe Keeper 与 Paprika 官方资料中反复出现的模式（证据与限制见 REFERENCES.md）：
- 外部内容导入
- 私人食谱库
- 购物清单
- 做饭使用
- 简单膳食计划

V1 不建设社区。

## 4. 成功标准

- 正常导入目标为分享 + 选择 Cook，不增加 Cook 内确认动作；第三方系统菜单的 More/Share to 等步骤与首次分享快捷设置需按平台实测，不能承诺所有平台总点击数固定为 2。
- 分享扩展不要求选分类、改菜名或等待 AI。
- AI 信息完整时自动入库。
- AI 信息不完整时仍保存，并精确标记待确认字段。
- 用户任何时候可返回原始来源核对。
- 导入失败必须提供可继续的降级路径，而不是只有“重试”。

## 6. 整理规则（产品提案 D1，待明确确认）

- “收藏”在外部分享语境表示收进私人食谱库；所有成功导入的食谱都已入库，不要求再点一次收藏。
- 库内偏好标记统一称“喜欢”，与入库、食谱册归属独立；取消喜欢不删除食谱。
- V1 只保留一套私人组织能力：用户自定义平级“食谱册”，不再同时建设另一套分类/标签树。同一食谱可属于零到多个册，关联不复制食谱。
- “全部”“未分类”“喜欢”“待完善”是系统筛选，不是用户可改名的册；未分类表示没有任何用户册归属。
- 创建/改名去除首尾空白，空名拒绝，同一用户内重名拒绝（大小写视为同名）；不预置必须填写的菜系/餐次。
- 从册移除只删除关联；删除册保留全部食谱，失去最后归属的食谱进入未分类。编辑同一食谱在全部册同步体现。
- 导入默认入“全部/未分类”，不自动猜分类、不要求分享时选册。批量整理、嵌套册、共享册后续评估。

## 7. 首个可用闭环边界（产品提案 D2）

首个可用版本须覆盖：收下 → 异步生成/异常补充 → 找到 → 按实际份量准备 → 做饭 → 买食材。简单周计划是 V1 后段，不作为这个闭环的前置条件。

- 建议基础份量调整和单个步骤计时进入首个闭环；原 P1 项移至上述 P0 提案，最终以 D2 确认为准。
- 基础份量调整只按目标份量/已知原份量乘以确定数量；保留原食谱，当前烹饪和购物使用所选份量快照。2 人份 100g 改 4 人份应为 200g。
- 原份量未知、区间或含义不明时禁止按人数自动换算，可查看原量或先由用户补充；“适量/少许/未知”原样保留。时间、温度不按倍数缩放；不做质量/体积密度猜测和营养计算。
- 步骤有明确时长才提供一键计时；模糊时长保留原文。单计时支持暂停/继续/取消；切步骤不重置，离开前台按实际截止时间恢复。锁屏提醒依赖通知权限，拒绝权限仍可做饭，前台可查看到期状态；终止 App 后恢复需验收，不能仅靠前台递减计数。

## 8. 离线与数据可携带性

离线最低要求是设备已成功保存的食谱文本（食材、步骤、原份量、来源信息）、搜索/系统筛选、做饭、D2 确认后的基础份量调整及购物清单。已经下载的封面应可见，未下载图片可缺省；不承诺所有原视频和第三方页面离线。

- 飞行模式冷启动可打开已保存食谱；来源 URL 仍可查看/复制，外链打开提示需联网。
- 已有购物清单可查看、勾选、增删改并持久化；离线从已保存食谱加入食材可用。杀进程重开不丢本地更改。
- 恢复网络后购物变更仅提交一次，不重复添加/合并；冲突不得静默丢掉未同步操作。具体冲突合同由工程 Issue 冻结。
- 新导入/AI 解析需联网。离线分享只有持久化输入成功后才能显示“已收下”，联网后补传；本地接收失败必须反馈失败，不能假成功。

导出最小范围提案 D3：用户主动导出全部已保存食谱的版本化 JSON 与可直接阅读的 HTML，包含标题、食材原文/数量单位、步骤、原份量/时间、来源平台/URL/可取得的作者标题、喜欢、食谱册及关联、待完善状态/字段；已下载封面可随包附带，缺失附件必须在清单声明。不要导出账户凭据、后台任务日志、供应商密钥或未授权的原视频。

这属于食谱可携带导出，不宣称完整备份：购物/计划、全部证据媒体、全量恢复暂不包含。若选择“可恢复备份”，须增加版本兼容与恢复验收后才能使用该名称。未确认 D3 前禁止扩展实现范围。

## 9. 首次使用与账户原则（提案 D4）

首次启动默认食谱库，只教如何通过分享收下食谱；不做问卷、推荐兴趣、强制建册或开通知。权限在实际使用相机/通知等能力时请求。

账户方案必须在工程所有权合同前确认：推荐可先看教学与本地内容，在首次云解析前一次性登录；完成后正常分享不再要求登录或额外确认。失效会话仍可可靠本地收下并标记待登录补传，不能丢输入。离线缓存可用范围与退出/删除账户的清理策略需工程与隐私任务对齐。匿名先用再绑定是另一方案，不能未经确认引入账户迁移。

## 10. 待用户决策与冻结条件

| ID | 推荐选项 | 另一选项 | 影响 |
|---|---|---|---|
| D1 | 平级多归属食谱册 + 独立喜欢 | 单归属食谱册 + 独立喜欢 | 决定组织关系合同；两者都不要求导入选册 |
| D2 | 首个闭环加入基础份量和单计时 | 首个闭环先原份量阅读，份量/计时后移 | 后者必须同步取消首版按份量购物/一键计时承诺 |
| D3 | 首版 JSON + HTML 食谱导出 | 首版可恢复备份 | 后者需新增恢复、媒体完整性和版本兼容范围 |
| D4 | 首次云解析前登录 | 匿名先用、后绑定 | 后者需明确匿名所有权、迁移和丢设备风险 |

以上为可审阅提案，PR 合并不能代替用户明确选择。没有已确认设计图，任何对应页面/弹框/HUD 仍禁止正式 UI 开发。
