# Extractive owner draft API V1

Canonical specification: [DEV-291](https://linear.app/gengyun/issue/DEV-291). Parent: [DEV-79](https://linear.app/gengyun/issue/DEV-79). Reuse the completed [DEV-283](https://linear.app/gengyun/issue/DEV-283) turn validator and [DEV-285](https://linear.app/gengyun/issue/DEV-285) OpenAI adapter.

This is an additive, **not implemented or deployed**, default-disabled engineering contract. Its machine-readable sources are [OpenAPI](../schemas/recipe-draft-v1.openapi.json) and [JSON Schema](../schemas/recipe-draft-v1.schema.json). Existing import endpoints, worker state transitions, source records, Share Extension acknowledgment and private snapshot APIs remain unchanged. Fixture validation proves static consistency; it does not prove JWT, RLS, transactions, networking, billing or native behavior.

## Scope and identities

A session belongs to a verified, non-anonymous Supabase user and exactly one owned, completed `recipe_import_jobs` row. `auth.uid()` supplies owner identity. Clients cannot supply owner, context, evidence, provider, model, secret or arbitrary patch values. Unknown or foreign session/job/turn IDs return identical 404 errors. No guest or anonymous-Auth use is allowed.

Only existing job fields/evidence/review flags are used. The immutable job source/result stays separate from a session's approved overlay. A user's message is untrusted conversation text, not new extraction evidence. Suggestions must be continuous verbatim text from referenced existing evidence; no new sources, inspiration, inferred quantities, nutrition, permissions or replacement fields. Full AI creation and private Recipe save integration are outside this contract.

## Wire and operations

All UUIDs use canonical lowercase RFC UUID text. Revisions are positive decimal strings from `1` through `9223372036854775807`, never JSON numbers or job `updated_at`. Each body is a JSON object with no unlisted properties. Request body bytes are limited to 32768, including chunked bodies; invalid UTF-8 or duplicate JSON object keys are rejected as INVALID_INPUT. Clients poll explicitly; creation and turns do not promise queue execution or provider success.

| Operation | Input | Success |
| --- | --- | --- |
| POST `/recipe-draft-sessions` | owned `job_id`, UUID `client_request_id` | 201 Session; identical replay 200 |
| GET `/recipe-draft-sessions/{session_id}` | session UUID | 200 Session |
| POST `/recipe-draft-sessions/{session_id}/turns` | UUID `request_id`, `expected_revision`, message | 202 pending Turn; terminal identical replay 200 |
| GET `/recipe-draft-sessions/{session_id}/turns/{request_id}` | owned session + turn request UUID | 200 Turn, including pending |
| POST `/recipe-draft-sessions/{session_id}/turns/{request_id}/approval` | new UUID `request_id`, `expected_revision`, accept/reject, `selected_paths` | 200 ApprovalReceipt |

Creation is idempotent by `(owner_id, client_request_id)`: the same job returns the same session; a different job under the same key returns 409. Multiple deliberate sessions for one job are allowed; each has an independent overlay, while owner budgets remain shared. Creation returns only after the session/base context is durably committed. If the job is not completed, return 409 JOB_NOT_READY. Disabled mode returns 503 DRAFT_DISABLED without creating sessions, claims or reservations. A ready job with no review flags is permitted; turns then return a durable `no_review_needed` result with no provider use.

The Session representation contains IDs, revision, current effective status, immutable source lineage, effective fields/evidence/review paths, approved overlay and aggregate session budget. It does not expose another owner's identity, provider configuration, keys or private notes. Imported fields preserve their raw/normalized values, evidence IDs, confidence and origin; those base values are stored without destructive transformation. The draft context returned here exposes only raw value/evidence IDs/confirmation/origin needed by the extractive service, not the full source recipe or raw attachment. Unsupported review flags produce rejected INVALID_REVIEW_PATH, without a provider call; they require manual review and are not silently removed by the new server boundary. This is a stricter integration precheck; it does not change DEV-283’s existing internal unsupported-flag filtering implementation.

## Logical persistent records and privileges

These are required logical records, **not SQL to execute**. Implementations may choose equivalent transactionally enforced relations, but may not replace persistence with a process Map.

- `recipe_draft_sessions`: UUID id; owner FK to auth.users with cascade; job FK with cascade; unique `(owner_id, client_request_id)`; immutable job ID/source fingerprint/base-context JSON and base-context hash; bigint revision starting at 1; effective context hash; confirmed overlay JSON; created/updated timestamps; session settled/reserved tokens and dispatch count.
- `recipe_draft_turns`: owner/session FKs with cascade; UUID request_id; unique `(owner_id, session_id, request_id)`; canonical request hash; based_revision; immutable context snapshot/hash; pending/terminal outcome; persisted validated generation result; claim fencing token, lease expiry and dispatch state; reserved/settled tokens; created/finished timestamps. A terminal generation result is immutable; an attached approval decision is separate.
- `recipe_draft_approvals`: owner/session/turn FKs; unique `(owner_id, session_id, request_id)` for the approval body request UUID; canonical approval hash, selected paths, action, applied revision and stable receipt. At most one decision per turn; no client-selected proposal values.
- `recipe_draft_owner_budgets`: unique `(owner_id, utc_date)`; settled and reserved tokens. Each reservation stores its original UTC date. Settlement never moves an existing reservation into a new day.

All records are owner-private under RLS; authenticated clients can only select their own authorized representations, and have no direct INSERT/UPDATE/DELETE. Anonymous/PUBLIC have no data or RPC privileges. Trusted write paths must verify the JWT and carry explicit owner predicates on every row/FK/transaction. Service-role bypass of RLS is not authorization. Session creation requires both owner equality and the exact immutable completed-job snapshot; no cross-owner join is allowed. Account deletion cascades these private records. For a still-existing account, job/session deletion must not refund settled or dispatched/unknown reservations or delete the owner-day budget; otherwise repeated deletion would bypass the owner quota. Deletion atomically settles any dispatched/unknown reservation at 4096 in its original owner-day row, and may release only a provably predispatch reservation while invalidating its fencing token; a deleted session cannot later dispatch. Owner-day rows remain until their UTC window closes and every associated reservation has settled; retention after that is a separate operational policy. Job deletion removes dependent sessions; source attachment deletion does not change previously persisted non-secret evidence excerpts. Private recipe/snapshot rows are not modified or deleted by this API.

## Canonical hashes and context

Canonical request/context hashing uses UTF-8 RFC 8785 JSON Canonicalization Scheme (JCS) then lowercase SHA-256. Reject duplicate object keys, nonfinite numbers, invalid Unicode scalar text and integers outside the interoperable safe range in canonicalized numeric metadata; revision remains a string. JCS object keys sort by UTF-16 code units, arrays retain order, and there is no Unicode normalization. Implementations must use a compatible reviewed implementation and cross-language vectors, not ordinary JSON stringify as a canonical hash.

The turn request hash covers `{request_id, expected_revision, message}` exactly; whitespace and property order of the incoming JSON do not matter, message contents do. Owner/session are the unique-key scope. Context hash covers immutable base lineage plus effective `{status, fields, evidence, reviewFields}` and session revision; provider config is not client input. Capture these hashes and the context in the same transaction as the claim. The service caller maps verified owner/revision/request UUIDs to DEV-283 `ownerID/currentRevision/expectedRevision/requestID`, and maps stored snake_case review fields to its existing internal `reviewFields`. The original imported result is never rewritten.

`fields` are existing valid draft paths, `evidence` is a list of UUID-linked excerpts, and `review_fields` use the exact existing reviewed paths/groups. An accepted overlay field stores the selected raw text, evidence IDs, `origin=AI_suggested`, `user_confirmed=true` and confirmation revision. Overlay wins when synthesizing trusted context. Confirmed paths are never sent as candidate editable paths to the provider. After approval, remove review paths resolved by those confirmed fields; group flags remain while any real, unconfirmed group gap remains. No nonexistent sibling is considered confirmed. If revision or context changes, a late proposal may not be published or applied.

## Durable turn claim, fencing and recovery

1. In one transaction lock the owned session, matching turn key and owner-day budget in consistent order (session then budget). Check the feature switch, ownership, revision/context and request shape before any provider work.
2. Check the persistent key before making a new claim. Identical canonical request returns the stored pending/terminal outcome, even if the session's current revision later changes; original proposal remains bound to its old revision and cannot be approved against a new one. Different canonical request under the same key returns 409 IDEMPOTENCY_CONFLICT without dispatch or charging. Replays never recalculate an old outcome with new evidence. The approval decision can change the response's separate `decision` field; the generation result itself stays stable.
3. If there is no review gap, persist a `no_review_needed` terminal outcome without reservation. For a new eligible turn, reserve 4096 tokens and enforce session and owner ceilings in that same transaction; allocate a random fencing UUID and a 30-second lease. Return 202 only after the pending row, snapshot and reservation are durably committed. A default-disabled system creates nothing.
4. Before calling the provider, atomically verify the lease, current owner/revision/context and fencing token, change `dispatch_state=dispatched_unknown`, and increment the session dispatch count. **Commit this marker before the external call.** Recheck the fencing token and deadline immediately before invoking the transport. A crash after this marker but before actual network transmission is conservatively unknown; it is never assumed free or safe to resend.
5. Call only the selected trusted route/provider, bounded by a maximum 10-second outer deadline and DEV-283/285 limits. The trusted caller wraps the DEV-285 provider function with a turn/fencing-scoped closure, captures its already validated outer OpenAI usage.totalTokens before passing that same output into DEV-283, and persists that bounded usage together with the matching attempt/fencing result. DEV-283 deliberately strips usage from its returned proposal; never read usage from its Result, accept client/model inner JSON usage, or associate a late attempt’s usage with a new fencing token. Adapter rejection/no captured validated usage charges the full reservation. Persist a validated result only under the same fencing token and still-current context. Valid captured usage settles the reservation; invalid/absent usage or an unknown outcome settles the full 4096. The validated response may be `proposal`, `rejected` or `unavailable`; none saves a private recipe. Stale context settles conservative cost and persists rejected STALE_REVISION. Late results after a terminal recovery cannot replace it.
6. A lease expiring while still `predispatch` may be reclaimed with a new fencing token after checking revision and reservation; exactly one claim can cross the committed dispatch marker. If revision became stale, terminate without dispatch and release the reservation. A lease expiring in `dispatched_unknown` becomes stable recoverable `unavailable/PROVIDER_OUTCOME_UNKNOWN`, settles all 4096, and is **not** automatically dispatched again. Poll, identical replay and worker recovery never resend an unknown external call. An explicit new request UUID is a new attempt at the current revision, with a new reservation and budget check.

The dispatch marker is a transaction boundary, not a promise of exactly-once execution at a remote vendor. A process Map may be an optimization only after this durable contract is authoritative. Generation failure preserves the job, session base and confirmed overlay. Global disabling blocks new creation/dispatch/approval; already-owned GET reads remain available, and existing pending work is terminated without a new dispatch, using the same conservative settlement rules.

## Approval CAS and overlay

An approval requires a terminal proposal at its original `based_revision`, a matching current `expected_revision`, an undecided turn and the current matching context hash. Lock the owned session and turn in one transaction. Check the persistent approval request key first: exact replay returns the stable receipt even after revision advances; changed body is 409 IDEMPOTENCY_CONFLICT. A new request on an already decided turn is 409 TURN_ALREADY_DECIDED.

Accept requires 1–20 unique selected suggestion paths, all present in the persisted validated proposal and still unconfirmed in current context. The server takes values/evidence from that proposal; it never accepts raw patch values. Reject requires an empty path array. Both decisions advance the session revision exactly once using CAS; an exhausted bigint revision returns 409 REVISION_EXHAUSTED and makes no changes. Accept writes only the confirmed overlay and effective context; reject leaves overlay unchanged. Persist the decision and stable ApprovalReceipt atomically with revision advancement. Stale revision/context/changed source cannot apply partial changes. Approval never regenerates a provider result, spends tokens, changes source facts, publishes content or implicitly saves a private Recipe. User-triggered private Recipe save and snapshot CAS remain a separate future integration.

## Budgets and provider configuration

V1 is default-disabled. Fixed engineering defaults: 4096 tokens reserved per dispatch, at most 8 dispatch markers per session, 32768 settled+reserved tokens per session, and 65536 settled+reserved tokens per owner UTC day. All ceiling checks and reservations are atomic across instances. Predispatch reservations count against the remaining dispatch slots so multiple pending turns cannot overbook the eight slots. Reservation release before proven non-dispatch restores the slot; marking dispatch consumes it permanently, even on failure. Identical replay and approval cost nothing.

Only a valid vendor `usage.total_tokens` integer in 0..4096 can settle a lower cost; return excess reserved capacity to both the session and the original owner-day row. Missing/invalid usage, transport failure after marking dispatch, timeout, unknown crash and rejected untrusted responses settle 4096. These token accounting rules are conservative budget units, **not actual dollar billing or vendor reconciliation**. No retry/fallback sends an unbudgeted external request. Future adjustable policies need an explicit versioned change; these numbers are not claimed as current production configuration.

The trusted caller loads existing `ai_routes`, its `primary_model_id`, enabled `ai_models`, and the matching enabled `ai_providers`; this contract uses a separately configured route key `recipe_import_draft_v1` without creating an extra registry or pretending a row already exists. A missing/disabled route means 503 PROVIDER_UNAVAILABLE with no dispatch. Server configuration cannot be overridden by the client. Use the existing `_shared/ai-secret.ts` resolver through the DEV-285 closure. The caller resolves configuration and the real secret in bounded preflight while the claim is still predispatch, then constructs DEV-285 with a resolver closure returning that already resolved secret; the adapter never receives a client key. Resolver failure before dispatch consumes no vendor budget; record a stable unavailable result and release the reservation. Immediately before the external transport the same fencing token must still authorize dispatch.

The transport must enforce TLS with trusted CA, HTTPS trusted provider configuration, fresh DNS resolution with all returned addresses public, private/link-local/metadata/IPv4-mapped private rejection, connection pinning to validated addresses, no redirects, byte/deadline limits and AbortSignal cancellation. It must not use an unguarded default global fetch or send secrets to a redirected host. Probe/allowlisting alone does not establish safe dispatch. Bound resolver/config preparation before marking dispatch; after the committed marker, any unresolved preparation or network uncertainty is conservatively charged. Provider body/headers, keys and evidence text are not written to public logs; record only safe correlation IDs, status, model version and token accounting.

## Limits and error mapping

Reuse DEV-283/285 exactly: message 2000 Unicode scalar characters; 100 fields; 60 evidence excerpts; 1500 scalar characters per excerpt; 20000 total excerpt characters; 32768 UTF-8 bytes for prepared provider input/output; 3 questions of 300 characters; 20 suggestions with raw text1500/reason500; 4096 total tokens; OpenAI request/response bodies65536 bytes. Paths allow title/servings, ingredients[0..99].name/raw_text/amount, steps[0..99].instruction; only actual unconfirmed review paths can be proposed. Each suggestion references at least one known excerpt containing its exact raw text. Public JSON representations retain no unbounded provider text.

HTTP errors use `{code,message,recoverable,request_id}`. 401 AUTH_REQUIRED includes invalid/expired/anonymous credentials; 404 NOT_FOUND masks foreign ownership; 409 covers JOB_NOT_READY/STALE_REVISION/IDEMPOTENCY_CONFLICT/TURN_ALREADY_DECIDED/REVISION_EXHAUSTED; 413 INPUT_TOO_LARGE; 422 INVALID_INPUT/INVALID_EVIDENCE/INVALID_REVIEW_PATH; 429 BUDGET_EXHAUSTED; 503 DRAFT_DISABLED/PROVIDER_UNAVAILABLE; 500 INTERNAL_ERROR is generic and never exposes SQL/provider text. Invalid provider outputs and runtime failures after durable turn acceptance are terminal Turn generation outcomes, not an HTTP error pretending the turn was never accepted. Return 200 for durable terminal poll/replay, including unavailable/rejected. A pending turn is not a proposal.
